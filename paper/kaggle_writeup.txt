# Historical-Data Repair Contracts for Gemma Agents

*A Calibrated Resource for Compatibility and Persistence Repair*

Guilin Zhang

## Abstract

We release eight executable historical-data repair contracts across six Python projects, covering 65 historical files and 252 dependent observations of reading, continued use and persistence. The resource calibrates acceptance when an old format has lost information. Two source repairs satisfy all 84 observations of a jsonpickle contract, yet literal equality with the reference rejects 60 observations for one valid repair. A corrupting control satisfies none despite completing every load and restart. All eight upstream-derived backports pass their contracts. Of 32 completed Gemma 4 repair attempts, four satisfy both semantic checks and source review. Released artifacts include historical bytes, patches, retained failures and an API-free verifier. The contribution is an executable acceptance contract and calibration, grounded in a known upstream ambiguity. Code, data and paper: https://github.com/GuilinDev/historical-data-repair-contracts

## 1. Introduction

Consider an old file containing a floating-point column. Two producer processes save the same values, one as float32 and the other as float64. Their complete files are identical (Figure 1). An evaluator that requires each original width asks the reader to distinguish inputs it cannot distinguish. Yet accepting any successful load is too weak: a reader can silently narrow a type or discard a later mutation.

Historical-data repair therefore needs an explicit acceptance contract. The test-oracle problem [1] is concrete here: which information survives in the file, which behavior must remain usable, and which alternative outputs are legitimate? We package those decisions with executable tasks rather than leaving them implicit in a single reference output.

![A float32 frame and float64 frame with column x and values 1.125 and -3.25 both produce the identical 267-byte old JSON document. A reader cannot uniquely infer the original width from that document. Values and numeric kind remain mandatory; ambiguous widths may widen.](https://raw.githubusercontent.com/GuilinDev/historical-data-repair-contracts/v0.1.0/paper/figures/figure1_collision.png)

Figure 1. Two historical producer states yield the same complete document. Each state self-roundtrips with its original width, but the saved bytes cannot distinguish them. The pair was found in six targeted producer executions; this is an existence witness, not a collision-rate estimate.

Each task supplies an affected reader, historical producer source, public examples and a limited source edit scope. A defect lineage groups one upstream defect and its fix with the relevant producer and reader versions. Different files and process repetitions within a lineage extend coverage; they are not independent bugs. We contribute eight such task bundles, an acceptance calibration and a completed Gemma baseline. Table 1 combines resource coverage, control outcomes and model results.

### Contract example: a writable joblib mapping

The agent receives a joblib 1.2.0 file and may edit joblib/numpy_pickle.py (plus an optional test). In this public case, the affected reader changes 23 to 91234 in memory and in the explicit resave, but the work file still contains 23 after flush. Checking both files in new processes detects the lost write-through.

```python
work = temporary_copy(historical_file)
a = joblib.load(work, mmap_mode="r+")
assert a.flat[1] == 23
a.flat[1] += 91211
a.flush()
joblib.dump(a, resaved_file)
for path in (work, resaved_file):
    b = fresh_process(joblib.load, path)
    assert b.flat[1] == 91234
```

Simplified from the executed verifier for one public case; fresh_process denotes a new interpreter. The full verifier also checks the remaining declared semantics.

## 3. Experiments: acceptance calibration

The jsonpickle defect was known upstream [2]: numeric tags can depend on runtime class-address order, which PYTHONHASHSEED does not fix. Our unmodified 4.1.1 producers generated the identical documents in Figure 1, while each self-roundtripped its original width. Let E_p be process p's encoder, and x_32 and x_64 be frames differing only in numeric width. Across processes p and q, E_p(x_32) = E_q(x_64). No file-only decoder can recover both original widths exactly.

For legacy numeric positions without explicit width suffixes, our contract requires exact values and numeric kind and permits nonnarrowing widths. Explicit historical widths and all new encodings remain exact. Differential testing already recognizes that different outputs can both satisfy a requirement [3]; the contribution here is an executable calibration of this particular contract.

We implemented three complete source-repair controls (Figure 2). The official conservative backport uses wide numeric types. Document exclusion v2 instead uses a producer invariant: each dtype name maps to one tag within a document. An explicit tag therefore excludes its dtype from another bare tag. A unique remaining candidate is used only for a nonempty, kind-compatible payload within the declared native-pandas numeric universe; otherwise the repair keeps the conservative fallback. A third repair deliberately narrows explicit float64 values.

![Paired horizontal bars start at zero. Conservative backport: 84 of 84 admissible and exact. Document exclusion v2: 84 of 84 admissible, 24 of 84 exact. Explicit-width narrowing: zero under both criteria. No uncertainty intervals because these are complete fixed-corpus counts, not independent samples.](https://raw.githubusercontent.com/GuilinDev/historical-data-repair-contracts/v0.1.0/paper/figures/figure2_calibration.png)

Figure 2. Complete source-repair controls on the numeric-code lineage. All three load and restart 84/84 observations. The alternate valid repair differs from literal reference output on 60 observations (five old files, twelve processes). These are researcher-built controls; literal equality is not the upstream test suite.

Both valid policies satisfy 84/84 observations. Literal equality with the official reader accepts only 24/84 for document exclusion. The remaining 60 are width-only differences on five files replayed in twelve processes; values, numeric kinds and subsequent operations agree with the contract. The narrowing control completes every load and restart but satisfies 0/84. Document exclusion uses explicit tags elsewhere in the same document. The witness in Figure 1 contains no such disambiguating tags, so this repair also falls back to float64.

These controls were written by the researchers, separately from Gemma. Source review found that v1 treated an empty column as evidence: Python's all(empty) is true, so a check intended to establish numeric type could pass without a value. We retained v1, guarded v2 against this case, and reran all 84 checks plus empty/nonempty pandas Interval columns, whose cells represent intervals. V2 matches the conservative reference but inherits its empty-Interval information loss. Arbitrary extension dtypes remain outside the validated scope.

## 4. Experiments: Gemma repair attempts

We ran Gemma 4 [4] on all eight tasks with two fresh conversations per deployment: A, 26B A4B through PrimeIntellect BF16; B, 31B through CoreWeave FP4. Provider and precision are confounded, hosted weight revisions are not attested, and public fixes may have appeared in pretraining.

Both deployments receive identical contracts, source tools and public checks, with up to 24 exploration rounds and 4,096 output tokens per exploration response. Both use temperature 0.2 during exploration and zero for the reserved 2,048-token final report. Exploration stops at a 120 KB request-context boundary. Acceptance requires every frozen observation and source review after delivery; the released protocol specifies tool, transport and retry limits.

All 32 conversations reached a valid final report and a decisive evaluation (Figure 3). Eight original PrimeIntellect rate-limit interruptions were resumed from identical saved requests, contexts and candidates, beyond the original three-retry ceiling. The failures and recovery journal remain in the release. Report completion records a finished attempt even when its delivered repair is incomplete.

Four repairs were accepted: A solved compressed joblib loading once; B solved endian-map persistence twice and historical CSV dispatch once. The endian patches retain the file-backed array instead of returning a converted copy. The CSV patch dispatches the old CSV representation before JSON decoding. Residual redundant code and untested internal-call paths still limit production use. No attempt supplies an optional regression test. Main-run API cost is US$0.7785.

Trajectory diagnosis. Sixteen attempts leave source unchanged; twelve edit it without satisfying the full contract. The fifteen context-bound stops comprise ten unchanged, four edited-incomplete and one accepted attempt. Exact-text edits fail 78 times across eleven attempts, including only five of the sixteen unchanged attempts; these errors cannot explain all unchanged outcomes. Three attempts encounter UTF-8 search errors. In one SQLAlchemy conversation, twelve edits target a two-line snippet occurring twice and are rejected by the unique-match guard. The competition's edit_file interface likewise defaults to allow_multiple=False [5]. This motivates testing location-aware editing; our traces do not measure official-harness failure rates. An unchanged packaging attempt reads the same 100-line window eight times. After logged round 20, its next request reaches 125,578 bytes, above the 120,000-byte guard; round 21 is not sent. These are request bytes, not tokens or measured model capacity.

A separate CSV attempt passes all six historical initial checks but fails all six restarts and all six current-format cases. Its broad legacy-reader dispatch produces an index-length mismatch after resaving: initial semantics alone do not establish persistence.

## 5. Related work

Compatibility testing predates coding agents. DUPTester studies distributed-system upgrades [6]. OpenHands' persistence CI uses payloads from released PyPI versions, golden fixtures and release cutoffs [7]. SWE-bench [8] already includes historical ECSV compatibility, while GitChameleon studies version-conditioned API code generation [9]. Our scope is narrower: repairing a reader against immutable old artifacts and a declared persistence contract.

Repair overfitting [10] motivates evaluating beyond construction tests. SWE-Gate separates functional success from further constraints [11], and UTBoost strengthens SWE-bench evaluation through additional tests [12]. Mokav and ChangeGuard compare program behaviors [13,14]; metamorphic testing studies relations between executions [15]. Our save/reload checks and differential controls use established testing ideas.

The calibration tests both boundaries of acceptance: reject corruption and admit valid alternatives. A separate comparison with genuine upstream tests covers 12 development attempts from packaging and attrs (nine candidate snapshots). Both evaluators accept the same two and reject the same ten; no added rejection is observed among the two upstream accepts. A timed-out preservation grid is not counted as a semantic failure: a completed regression test already rejects that patch. These attempts are separate from the main 32, and Figure 2 compares literal outputs rather than authentic upstream suites.

## 6. Availability and limits

Resource card. Eight lineages, six projects, 65 files and 252 dependent observations. The release contains producer/reader source, reference and model patches, frozen expectations, licenses and retained failures. Original contributions use Apache-2.0; third-party licenses are retained. The qualified runtime is Linux ARM64 with Docker. Download and instructions: https://github.com/GuilinDev/historical-data-repair-contracts

Start with python3 compat.py integrity. This checks file hashes, not repair semantics. After the documented environment bootstrap, run python3 compat.py reproduce --task joblib_endian_1561 --controls base,fixed,reference for a complete task. A fresh dependency installation on the same ARM64 host reproduced all 24 control evaluations (756 observations). Release-only replay of 32 patches completed 1,008 observations and preserved the four full acceptances. Two incorrect dtype readers changed partial counts across processes; replay adds no model attempts.

Expected observations and admissibility were frozen before model calls; allowed-file upstream backports pass 252/252 checks. Historical bytes, producer source, expectations and verifier code remain immutable during repair. Agents edit designated Python files and may add a regression test. Execution uses network-disabled, read-only ARM64 containers with one CPU, 1 GB memory and temporary working copies. Source review excludes fixture hardcoding and verifier manipulation.

Limits. Eight selected lineages do not estimate defect prevalence or general coding ability. Most are upgrade regressions; compressed joblib loading is a longstanding defect, and dtype tags vary across processes. Two joblib fixes share a project. Only one lineage calibrates ambiguous outputs; its six files repeated across processes are not new artifacts. The edit allowlist supplies localization and excludes dependency/native-code fixes. Finite checks cover only declared behavior; other architectures remain unqualified.

## 7. Conclusion

- Repair contracts should test continued use and persistence, beyond successful loading.
- Acceptance calibration must reject corruption while admitting alternatives allowed by missing historical information.
- Eight executable tasks and 32 completed Gemma attempts provide a reproducible baseline: four repairs satisfy the full contract and source review.
